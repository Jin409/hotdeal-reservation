# PR 본문 작성 가이드

동료가 컨텍스트 없이 읽어도 이해할 수 있도록 작성합니다.
변경 사항(무엇)과 의도(왜)를 모두 담습니다.

## 언제 사용하나요?

- PR 본문을 새로 작성할 때
- PR 본문을 수정하거나 보완할 때

## 템플릿

```markdown
## 배경

이 PR이 왜 필요한지 1~3문장으로 작성합니다.

## 변경사항

- 변경한 내용 1
- 변경한 내용 2

## 기술적 판단

핵심 구현에서 왜 이 방식을 선택했는지 작성합니다.
DECISIONS.md에 이미 있는 내용은 링크로 대체합니다.

## 시퀀스 다이어그램

로직이 있는 경우에만 작성합니다. 없으면 섹션을 생략합니다.

\```mermaid
sequenceDiagram
    ...
\```

## 테스트

어떤 시나리오를 검증했는지 작성합니다.

- 단위: ...
- 서비스: ...
- 인수: ...

## 참고

- 관련 이슈: #이슈번호
- 관련 DECISIONS.md 쟁점: 쟁점 N. 제목
```

## 필수 규칙

- 배경은 구현 내용이 아니라 **이유**를 작성합니다.
- 변경사항은 파일명이 아니라 **기능 단위**로 작성합니다.
- 기술적 판단은 핵심 판단 **1~2개**만 작성합니다. 모든 구현을 나열하지 않습니다.
- 시퀀스 다이어그램은 로직이 있는 PR에만 작성합니다. 단순 CRUD는 생략합니다.
- 테스트는 "작성했습니다"가 아니라 **어떤 시나리오를 검증했는지** 작성합니다.

## 좋은 예 / 나쁜 예

**배경**
```
❌ BookingController와 BookingService를 구현합니다.
✅ 사용자가 대기열에 진입하고 순번을 받을 수 있어야 하므로
   POST /bookings API를 구현합니다.
```

**변경사항**
```
❌ BookingController.java 추가
❌ BookingService.java 추가
✅ POST /bookings API 구현 (대기열 진입 + 순번 반환)
✅ 유저당 중복 대기열 진입 방지 처리
✅ 복합결제 혼용 검증 (CREDIT_CARD + YPAY 차단)
```

**기술적 판단**
```
❌ Redis를 사용했습니다.
✅ 대기열 중복 진입 방지를 위해 Redis SET을 사용했습니다.
   DB로 처리하면 매 요청마다 조회가 발생하여
   고TPS 환경에서 부담이 크기 때문입니다.
```

**테스트**
```
❌ 테스트 코드를 작성했습니다.
✅ 동일 유저가 두 번 대기열 진입 시 1번만 진입되는지 검증
✅ CREDIT_CARD + YPAY 혼용 요청 시 400 응답 검증
```
